# Ticket Bot Security: Permanent Engineering & Research Rules

This skill defines the non-negotiable rules, constraints, ethical boundaries, and development practices for the **AI-Based Behavioral Bot Detection and Adaptive Cybersecurity for Secure Online Ticket Booking** research prototype.

Every agent working on this codebase MUST abide by these guidelines.

---

## 1. Ethical Boundaries & Case Study Simulation

1. **NO PRODUCTION INTERACTION:** Never connect to, scrape, test against, attack, or automate the real IRCTC production portal or any real-world ticketing system.
2. **STRICT LOCAL SIMULATION:** All operations, telemetry collection, bot simulation, and payment flows occur strictly against our locally controlled `localhost` Flask application.
3. **SIMULATED PAYMENTS ONLY:** Never integrate real payment gateways or process genuine credit/debit card numbers or UPI handles. Simulated payments are purely tokenized state transitions.
4. **NO CAPTCHA BYPASSING RESEARCH:** Do not build or deploy tools designed to defeat real commercial CAPTCHAs or real anti-bot systems.

---

## 2. Machine Learning & Behavioral Detection Principles

1. **SELENIUM IS A GENERATOR, NOT THE DETECTOR:**
   - Selenium is used exclusively as a controlled generator of automated sessions across defined behavioral profiles.
   - The detector must NEVER inspect `navigator.webdriver`, headless user-agent tokens, or browser automation artifacts.
   - The ML model must learn strictly from human vs. automated physical and behavioral telemetry.
2. **MULTI-SIGNAL FUSION IS MANDATORY:**
   - Detection must integrate multiple independent interaction channels: keystroke dynamics, cursor kinematics, scroll hesitation, and form dwell times.
   - Single-feature heuristics (e.g., "typing speed > 600 cpm") are strictly prohibited as primary detectors.
3. **STRICT SESSION-BASED SPLITTING (NO DATA LEAKAGE):**
   - Datasets must be partitioned strictly by entire `session_token` and `user_id`.
   - Never randomly split events or windows from the same session between train and test sets.
4. **UNSEEN AUTOMATION PROFILE EVALUATION:**
   - The test split must evaluate at least one bot profile (e.g., randomized delays or alternate navigation paths) that was never seen during training.
5. **SYSTEMATIC ABLATION STUDIES:**
   - Always run and report the ablation study comparing individual modalities (keystroke only, mouse only, session only, keystroke + mouse) against the full multi-signal pipeline to quantify fusion gain.
6. **NEVER FABRICATE ML RESULTS:**
   - All metrics (Accuracy, Precision, Recall, F1, FPR, FNR, latency) must be real empirical outputs generated by running the evaluation scripts.

---

## 3. Adaptive Security & Graduated Defense

1. **NO PERMANENT BANS ON SINGLE INFERENCE:**
   - Probabilistic ML predictions must never result in an immediate permanent IP or account ban.
2. **GRADUATED THREE-TIER RESPONSE:**
   - **Low Risk (0–39):** Allow normal, frictionless booking.
   - **Medium Risk (40–69):** Trigger an interactive cognitive verification challenge before seat reservation.
   - **High Risk (70–100):** Apply dynamic rate-limiting (token bucket delay queue) and temporary session throttling for the active reservation window.
3. **FALSE-POSITIVE PROTECTION:**
   - Design and tune detection thresholds specifically to keep False Positive Rates on human sessions under 2%.
   - Protect users with motor variations, screen readers, or assistive input devices.

---

## 4. Privacy & Data Minimization (Privacy by Design)

1. **NO RAW KEYSTROKE CAPTURE:**
   - Never record actual typed characters, key codes, or input strings in telemetry tables.
   - Record only temporal deltas ($\Delta t$ between keydown and keyup, and inter-key intervals).
2. **SENSITIVE FIELD EXCLUSION:**
   - Keystroke and input telemetry must automatically bypass password fields (`<input type="password">`) and simulated payment inputs.
3. **ANONYMIZED IDENTIFIERS:**
   - Store sessions and behavior records using randomly generated UUIDs.
   - Never store plain text passwords; use salted PBKDF2-SHA256 password hashing.

---

## 5. Development & Verification Protocol (Karpathy Guidelines)

1. **INCREMENTAL EXECUTION:**
   - Follow the 16 defined phases sequentially (Phase 00 to Phase 15).
   - Never build the entire project in one unverified blast.
2. **VERIFY AT EVERY STEP:**
   - Run unit/integration tests (`pytest tests/`).
   - Run the application on `localhost` and verify in the browser.
   - Inspect backend logs and check for console errors.
   - Fix all issues before declaring a phase complete.
3. **SURGICAL & SIMPLE CODE:**
   - Write clean, minimal code that directly solves the requirement without speculative over-engineering.
   - Maintain existing docstrings and structure.
